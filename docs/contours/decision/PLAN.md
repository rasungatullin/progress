# План реализации контура принятия решения

## 1. Назначение документа

Настоящий документ фиксирует прикладной план реализации контура принятия решения в составе комплекса «Прогресс». План построен не от общей архитектурной полноты, а от того рабочего результата, который требуется получить на каждом следующем шаге развития.

Основной сценарий принят в следующем виде:

1. получить номер задачи;
2. запустить обработку задачи;
3. провести задачу через кодирование, запрос на слияние, ревизию, доработку и слияние;
4. затем расширить контур режимами проверки готовности задачи и синтеза подробного описания.

## 2. Целевой приоритет развития

Для данного контура приоритетом является не абстрактная универсальность маршрутизации, а как можно более ранний ввод замкнутого рабочего цикла по задаче разработки.

Приоритет шагов принимается в следующем порядке:

1. запуск рабочего цикла по номеру задачи;
2. передача задачи в исполнительный контур кодирования;
3. открытие запроса на слияние по указанию исполнительного каскада;
4. запуск ревизии и постановка замечаний к коду;
5. передача замечаний на доработку и повторная ревизия;
6. слияние запроса при положительном заключении ревизии;
7. проверка готовности задачи к исполнению;
8. синтез подробного описания задачи.

Именно в этом порядке должны быть ориентированы ближайшие этапы реализации.

## 3. Принцип планирования

Каждый этап должен завершаться не только кодом, но и новым эксплуатационным состоянием контура. После завершения этапа должно быть понятно, какой новый режим работы появился в комплексе и какой фрагмент полного цикла теперь можно пройти без ручного обхода логики.

Промежуточные стадии считаются достаточными только в том случае, если:

- их можно вызвать через CLI;
- результат выражен в формализованном решении или формализованной команде следующему контуру;
- новый шаг в целевом процессе действительно замыкается на практике.

## 4. Этап 1. Запуск рабочего цикла по номеру задачи

Цель этапа — получить минимальную точку входа, в которой контур принимает номер задачи и запускает целевой сценарий обработки.

Результат этапа:

- появляется команда запуска рабочего цикла с указанием номера задачи;
- контур умеет принять номер задачи как основной входной идентификатор;
- по номеру задачи контур может получить исходную карточку через интеграционный контур;
- формируется первичный `DecisionContext` для дальнейшей маршрутизации.

После данного этапа запуск обработки задачи больше не требует ручной подготовки полного входного контекста.

Минимальные работы:

- определить формат входа по номеру задачи;
- определить, какая интеграция считается первичным источником карточки задачи;
- реализовать команду полного запуска по номеру задачи;
- реализовать преобразование карточки задачи во внутренний контекст рассмотрения;
- покрыть тестами сценарий «номер задачи -> внутренний контекст».

## 5. Этап 2. Прямая передача задачи кодирующему каскаду

Цель этапа — сделать так, чтобы контур решения на первом рабочем шаге просто направлял задачу в исполнительный контур кодирования.

Результат этапа:

- по поступившей задаче контур способен принять решение `execute`;
- решение формирует задание для кодирующего каскада;
- задание содержит минимум сведений, достаточных для запуска исполнения;
- команда полного вызова может провести задачу до фактического старта кодирования.

После данного этапа появляется первый практически полезный рабочий режим: задача по номеру поступает в систему и уходит в работу кодирующему каскаду.

Минимальные работы:

- определить минимальную модель решения для режима `execute`;
- определить минимальную форму задания для кодирующего каскада;
- связать решение с веткой `execution`;
- зафиксировать причины выбора режима `execute`;
- покрыть тестами сценарий «номер задачи -> запуск кодирования».

## 6. Этап 3. Открытие запроса на слияние по команде исполнительного каскада

Цель этапа — научить контур решения принимать структурированную команду от кодирующего каскада на открытие запроса на слияние.

Результат этапа:

- исполнительный каскад может вернуть признак готовности к открытию запроса на слияние;
- контур решения распознаёт этот результат как отдельный следующий шаг;
- по структурированному выходу кодирующего каскада запускается открытие запроса на слияние;
- в состоянии задачи фиксируется переход из режима кодирования в режим ревизии.

После данного этапа контур перестаёт завершаться на кодировании и начинает вести задачу дальше по инженерному циклу.

Минимальные работы:

- определить структурированный признак или команду открытия запроса на слияние;
- согласовать этот выход с исполнительным контуром;
- определить решение, которое инициирует вызов интеграции создания запроса на слияние;
- покрыть тестами переход «результат кодирования -> открытие запроса на слияние».

## 7. Этап 4. Запуск ревизии и постановка замечаний к коду

Цель этапа — перевести контур в режим координации ревизии после открытия запроса на слияние.

Результат этапа:

- контур способен инициировать исполнительный каскад ревизии;
- ревизионный каскад получает контекст запроса на слияние и изменения кода;
- по результату ревизии контур ставит замечания к коду через интеграционный контур;
- состояние задачи получает явный режим «ожидаются доработки» или «замечаний нет».

После данного этапа контур уже умеет не только открыть запрос на слияние, но и провести его через автоматизированную ревизию.

Минимальные работы:

- определить решение запуска ревизионного каскада;
- определить минимальный вход ревизии: запрос на слияние, diff, комментарии, контекст задачи;
- определить структурированный выход ревизии;
- реализовать передачу замечаний в интеграционный контур постановки комментариев;
- покрыть тестами сценарий «запрос на слияние -> ревизия -> комментарии».

## 8. Этап 5. Передача замечаний на доработку и повторная ревизия

Цель этапа — замкнуть цикл доработки по замечаниям ревизии.

Результат этапа:

- контур способен собрать замечания ревизии в формализованный вход для кодирующего каскада;
- кодирующий каскад получает задачу не с нуля, а как доработку по замечаниям;
- после завершения доработки контур повторно запускает ревизию;
- цикл «ревизия -> доработка -> повторная ревизия» становится воспроизводимым.

После данного этапа появляется первый полноценный замкнутый цикл сопровождения запроса на слияние.

Минимальные работы:

- определить представление замечаний ревизии для повторной передачи в кодирование;
- реализовать решение о запуске доработки;
- реализовать решение о повторной ревизии после доработки;
- ввести признак номера цикла ревизии или итерации доработки;
- покрыть тестами сценарий «замечания -> доработка -> повторная ревизия».

## 9. Этап 6. Слияние запроса на слияние при положительном заключении ревизии

Цель этапа — довести основной инженерный цикл до автоматизированного завершения.

Результат этапа:

- контур различает состояние, при котором запрос на слияние допускается к слиянию;
- положительное заключение ревизии становится формализованным основанием для следующего шага;
- при отсутствии блокирующих замечаний и при соблюдении условий контур инициирует слияние;
- цикл обработки задачи может завершиться без ручного переключения между стадиями.

После данного этапа основной путь «задача -> кодирование -> запрос на слияние -> ревизия -> доработка -> ревизия -> слияние» становится замкнутым.

Минимальные работы:

- определить условия перехода к слиянию;
- определить формализованный признак положительного заключения ревизии;
- связать решение со стадией слияния через интеграционный контур;
- зафиксировать журнал оснований для автоматического слияния;
- покрыть тестами сценарии успешного и запрещённого слияния.

## 10. Этап 7. Проверка готовности задачи к исполнению

Цель этапа — добавить перед основным циклом режим предварительной оценки задачи.

Результат этапа:

- контур способен отдельно запускать проверку готовности задачи к исполнению;
- по задаче формируется одно из двух основных заключений: задача готова к исполнению или задача требует подробного описания;
- результат проверки становится самостоятельным режимом решения, а не побочным текстовым заключением;
- режим проверки можно вызвать отдельно от основного кодирующего цикла.

После данного этапа контур получает предвходной режим сортировки задач до их отправки в кодирование.

Минимальные работы:

- определить критерии готовности задачи к исполнению;
- определить признаки недостаточности постановки;
- ввести отдельный режим решения для проверки готовности;
- реализовать CLI-вызов проверки готовности;
- покрыть тестами сценарии «готова к исполнению» и «требует подробного описания».

## 11. Этап 8. Синтез подробного описания задачи

Цель этапа — научить контур запускать построение подробного описания для задач, признанных недостаточно проработанными.

Результат этапа:

- по итогам проверки готовности контур способен направить задачу в режим синтеза подробного описания;
- формируется отдельное задание на построение подробной постановки;
- результат синтеза может быть возвращён в задачу как дополнительное описание или рабочий артефакт;
- после появления подробного описания задача может повторно пройти проверку готовности.

После данного этапа контур покрывает не только цикл исполнения уже готовых задач, но и цикл доведения недостаточно определённых задач до исполнимого состояния.

Минимальные работы:

- определить тип решения для синтеза подробного описания;
- определить входные данные для соответствующего исполнительного каскада;
- определить, куда возвращается результат подробного описания;
- реализовать повторный вход задачи в проверку готовности;
- покрыть тестами сценарий «недостаточно определена -> подробное описание -> повторная проверка».

## 12. Первый практически достаточный срез

Первый практически достаточный срез контура должен давать следующий результат:

1. запускается рабочий цикл по номеру задачи;
2. задача передаётся кодирующему каскаду;
3. по команде кодирующего каскада открывается запрос на слияние;
4. по запросу на слияние запускается ревизия;
5. замечания ревизии возвращаются на доработку;
6. после доработки запускается повторная ревизия;
7. при положительном заключении ревизии запрос на слияние сливается.

Если этот срез достигнут, основной инженерный цикл можно считать минимально рабочим.

## 13. Второй практически достаточный срез

Второй практически достаточный срез должен добавлять к первому следующий результат:

1. задача может быть предварительно проверена на готовность к исполнению;
2. задача может быть помечена как требующая подробного описания;
3. по такой задаче запускается синтез подробного описания;
4. после этого задача возвращается в контур проверки готовности и затем в основной цикл исполнения.

Если этот срез достигнут, контур начинает покрывать не только исполнение уже понятных задач, но и доведение неготовых задач до исполнимого состояния.

## 14. Критерии завершения первой версии

Первая версия контура может считаться завершённой, если одновременно выполняются следующие условия:

- задача может быть запущена по номеру через одну команду полного вызова;
- основной цикл кодирования, запроса на слияние, ревизии, доработки и слияния проходит через формализованные решения контура;
- переходы между стадиями выражены в данных, а не в неформализованных текстовых договорённостях;
- повторная ревизия после доработки выполняется как штатный режим;
- режим проверки готовности и режим синтеза подробного описания вызываются отдельно и не смешиваются с основным кодирующим циклом;
- ключевые переходы покрыты тестами и наблюдаемы через CLI.

## 15. Направления расширения после первой версии

После ввода первой версии развитие контура может идти по следующим направлениям:

- расширение типов задач и типов инженерных сценариев;
- перенос правил принятия решения из кода в конфигурацию;
- накопление статистики по качеству прохождения циклов ревизии;
- управление ограничениями слияния, окнами выполнения и политиками допуска;
- интеграция с проектным состоянием и контекстным архивом;
- подключение дополнительных режимов аналитического синтеза по задаче.

Эти направления следует начинать только после того, как будут стабилизированы первый и второй практически достаточные срезы.
