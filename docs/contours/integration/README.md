# Контур интеграции с внешними системами

## 1. Назначение

Контур интеграции с внешними системами предназначен для получения, поиска и унификации сведений, необходимых для принятия решения и исполнения задач.

## 2. Основной состав

В состав контура входят:

- диспетчер интеграционных модулей;
- адаптеры внешних систем;
- подсистема нормализации внешних объектов;
- подсистема кэширования и повторного использования контекста;
- подсистема контроля доступности и отказов.

## 3. Основные функции

- подключение к внешним API и служебным интерфейсам;
- поиск данных по объектам задачи;
- извлечение документов, параметров, состояний и артефактов;
- кэширование повторно используемых сведений;
- унификация ответов разнородных источников;
- контроль полноты и доступности получаемой информации.

## 4. Входы и выходы

Входы:

- запросы на получение контекста;
- идентификаторы объектов и событий;
- указания от контура принятия решения;
- указания от контура исполнения.

Выходы:

- структурированные данные внешних систем;
- документы и артефакты;
- нормализованные представления объектов;
- признаки доступности или недоступности источников.

## 5. Внутренние элементы

### 5.1 Диспетчер интеграционных модулей

Диспетчер принимает внутренний запрос, определяет нужный адаптер, управляет политикой вызова, повторными попытками и нормализует итоговый результат к единому контракту.

### 5.2 Адаптер внешней системы

Адаптер инкапсулирует особенности конкретного источника: способ авторизации, формат вызова, набор поддерживаемых операций, преобразование ошибок и извлечение артефактов.

### 5.3 Нормализатор внешних объектов

Нормализатор переводит сущности внешней системы во внутренние типы комплекса: задачу, комментарий, change request, ссылку на репозиторий, пользователя, состояние, документ и артефакт.

### 5.4 Подсистема кэширования

Подсистема кэширования удерживает результаты повторно используемых запросов в пределах жизненного цикла обработки, чтобы снизить число внешних обращений и сохранить воспроизводимость принятого решения.

### 5.5 Подсистема контроля доступности

Подсистема фиксирует недоступность источников, ошибки авторизации, превышение лимитов и неполноту ответа, чтобы другие контуры могли отличать отсутствие данных от отказа внешней системы.

## 6. Первый трекер: GitHub через `gh`

В качестве первого практического адаптера принимается GitHub. Взаимодействие должно строиться не через прямую работу с REST API, а через штатную утилиту `gh`, выступающую локальным шлюзом доступа к GitHub.

Такой выбор задаёт следующие правила:

- авторизация и хранение токена делегируются `gh`;
- первичная интеграция использует вызовы `gh` как внешний исполняемый инструмент;
- контур интеграции отвечает за формирование аргументов, чтение результата, нормализацию и обработку ошибок;
- формат внутреннего ответа не должен зависеть от конкретного текстового вида CLI-вывода `gh`, поэтому для машинных вызовов предпочтительны `gh api`, `gh issue view --json`, `gh pr view --json` и иные JSON-режимы.

GitHub на первом этапе рассматривается как трекер задач и изменений, из которого требуется получать:

- карточки issue;
- pull request;
- комментарии и review-комментарии;
- метки, состояния, исполнителей, milestone;
- сведения о репозитории, ветках и связанных ссылках.

## 7. Архитектурная роль

Контур выступает поставщиком сведений из внешней среды. Он обеспечивает другие контуры данными из трекеров задач, документации, репозиториев и иных служебных систем.

При наличии GitHub-адаптера контур интеграции становится источником нормализованных сведений о задачах разработки и изменениях в коде, которые затем используются контуром принятия решения и контуром исполнения.
