# Целевая архитектура контура интеграции

## Назначение документа

Документ описывает целевое состояние контура интеграции с внешними системами. Он фиксирует назначение контура, его границы, внутреннее устройство, основные сущности и правила взаимодействия с другими контурами комплекса.

Документ не заменяет практические контракты первого среза. Текущие команды, Go-типы и адаптер GitHub описываются в `README.md`, `CONTRACTS.md` и `CLI.md` настоящего раздела.

## Задача контура

Задача контура интеграции — обеспечить другие контуры стандартной интеграцией с внешними источниками.

Контур должен дать комплексу единый способ получать и изменять внешние объекты: задачи, запросы на слияние, репозитории, комментарии, обсуждения, сообщения, пользователей, артефакты и связанные служебные данные. Остальные контуры не должны знать, как устроена конкретная внешняя система, где она хранит поля, как выполняет авторизацию и какие ограничения накладывает на операции.

Ключевая идея контура состоит в том, что комплекс работает не с исходными форматами внешних систем, а с каноническими структурами. Эти структуры подбираются под процессы комплекса и инженерный смысл объектов, а не под устройство конкретного трекера, хранилища кода или средства коммуникации.

## Место в основном цикле

В базовом цикле обработки контур интеграции выполняет две группы функций.

На входе обработки контур получает от контура реакции параметры запроса данных. По этим параметрам он обращается к внешним источникам, собирает полный набор данных и возвращает каноническую задачу со связанными каноническими объектами.

На выходе обработки контур получает от контура исполнения операции изменения. Он преобразует их в вызовы конкретных внешних систем и возвращает диагностируемый результат: изменение выполнено, выполнено частично, не выполнено из-за отказа или отклонено как неподдерживаемое.

Контур принятия решения в целевой модели работает с уже восстановленными каноническими данными. Если для проверки маршрута нужны дополнительные сведения, они должны быть либо заранее включены в набор данных, либо запрошены через явно описанную интеграционную операцию, не размывающую границы ответственности.

## Границы ответственности

Границы контура следуют из его задачи: он стандартизует вход и выход внешних источников. Внутри границы находятся выбор интегрируемой системы, получение или изменение внешнего объекта, приведение результата к канонической форме и нормализация отказного состояния.

Контур интеграции не выбирает следующий инженерный шаг, не выполняет маршрут обработки, не подготавливает исполнительное окружение и не хранит текущее состояние рабочей задачи как собственный источник истины.

Текущее состояние рабочего объекта находится во внешнем источнике. Контур интеграции восстанавливает это состояние для конкретной обработки и может выполнить изменение, но не становится владельцем долговременного состояния объекта.

## Типы интеграций

Тип интеграции определяет класс внешних систем, набор канонических объектов и типовые операции. Это позволяет не смешивать задачу, запрос на слияние, репозиторий и сообщение в одну сущность.

Минимальный целевой набор типов интеграций:

- трекер;
- репозиторий;
- мессенджер;
- `wiki`.

Дополнительно может быть задан пользовательский тип интеграции. Например, система управления тестированием (`TMS`) может иметь собственные канонические объекты: тестовый набор, тестовый прогон, тестовый случай и результат проверки.

### Трекер

Трекер отвечает за рабочие задачи и их жизненный цикл.

Типовые канонические объекты трекера:

- каноническая задача;
- комментарий задачи;
- связь задач;
- пользователь;
- признак задачи;
- атрибут задачи.

Типовые операции трекера:

- получить задачу;
- найти задачи;
- получить комментарии задачи;
- создать комментарий;
- изменить признаки или атрибуты задачи;
- создать дочернюю задачу;
- связать задачи.

### Репозиторий

Репозиторий отвечает за кодовую базу, ветки, изменения и запросы на слияние.

Типовые канонические объекты репозитория:

- репозиторий;
- ветка;
- коммит;
- карточка запроса на слияние;
- замечание ревизии;
- состояние проверки;
- артефакт сборки или проверки.

Типовые операции репозитория:

- получить сведения о репозитории;
- получить ветку или коммит;
- получить запрос на слияние;
- получить замечания ревизии;
- открыть запрос на слияние;
- ответить на замечание ревизии;
- получить состояния внешних проверок;
- связать артефакт с изменением.

### Мессенджер

Мессенджер отвечает за внешние сообщения и обсуждения.

По умолчанию для мессенджера принимается модель цепочек обсуждения: цепочка обсуждения содержит сообщения и реакции сообщения.

Типовые канонические объекты мессенджера:

- канал или пространство сообщений;
- цепочка обсуждения;
- сообщение;
- реакция сообщения;
- пользователь.

Типовые операции мессенджера:

- получить цепочку обсуждения;
- получить сообщения цепочки обсуждения;
- создать сообщение;
- ответить в цепочку обсуждения;
- добавить или убрать реакцию сообщения;
- связать цепочку обсуждения с задачей или другим внешним объектом.

### Тип интеграции `wiki`

Тип интеграции `wiki` отвечает за внешние хранилища документации и связанные страницы.

Типовые канонические объекты типа интеграции `wiki`:

- страница документации;
- пространство документации;
- версия страницы;
- ссылка на страницу;
- пользователь.

Типовые операции типа интеграции `wiki`:

- получить страницу по идентификатору;
- найти страницы по запросу внешней системы;
- получить тело страницы в каноническом формате;
- получить версию и ссылку на страницу;
- связать страницу документации с задачей или другим внешним объектом.

## Интегрируемые системы

Для каждого типа интеграции может быть подключено несколько интегрируемых систем. Например, для типа «трекер» могут существовать разные системы задач, а для типа «репозиторий» — разные системы хранения кода.

Каждая интегрируемая система должна иметь уникальное имя внутри конфигурации комплекса. У каждого типа интеграции должна быть система по умолчанию. Если канонический запрос не указывает конкретную систему, контур интеграции использует систему по умолчанию для указанного типа. Если запрос указывает систему явно, реестр интеграции должен обратиться именно к ней.

Такое разделение позволяет маршрутам и действиям работать через тип интеграции, а при необходимости выбирать конкретный источник данных.

## Встроенные и пользовательские интеграции

Интеграция может быть встроенной или пользовательской.

Встроенная интеграция поддержана кодом комплекса. Для неё заранее известны адаптер, канонические объекты, типовые операции, правила нормализации и отказные состояния.

Пользовательская интеграция задаётся через внешние `sh`-скрипты. Такой вариант нужен для источников, которые важны конкретному проекту, но ещё не поддержаны в коде комплекса. Пользовательская интеграция должна соблюдать тот же канонический контракт: принимать структурированный запрос, возвращать канонический объект или отказное состояние и не заставлять другие контуры знать устройство внешней системы.

## Основные сущности

### Внешний источник

Внешний источник — система, в которой живут рабочие объекты комплекса. Источником может быть трекер задач, система хранения кода, средство сообщений, хранилище документов, реестр артефактов или локальный источник, используемый как внешний по отношению к основным контурам.

Важное свойство источника — он хранит фактическое состояние объекта, с которым могут работать и люди, и комплекс.

### Тип интеграции

Тип интеграции — класс внешних источников с собственными каноническими объектами и типовыми операциями. Тип отвечает на вопрос, с какой предметной областью работает контур: задачами, репозиториями, сообщениями или другой областью.

### Интегрируемая система

Интегрируемая система — конкретное подключение внешнего источника внутри выбранного типа интеграции. Она имеет уникальное имя, настройки доступа, правила отображения внешних данных и сведения о поддерживаемых операциях.

### Канонический объект

Канонический объект — нормализованное представление внешнего объекта внутри комплекса. Он должен выражать инженерный смысл объекта и быть пригодным для маршрутов, проверок и действий.

Набор канонических объектов определяется типом интеграции. Каноническая задача относится к трекеру, карточка запроса на слияние — к репозиторию, цепочка обсуждения и сообщение — к мессенджеру. Эти объекты могут быть связаны между собой, но не становятся частями одной большой задачи.

Канонические объекты могут содержать признаки и атрибуты. Признаки используются для коротких нормализованных состояний и классификации. Атрибуты используются для параметрических значений, которые не выражаются простым признаком.

### Канонический запрос

Канонический запрос — обращение к контуру интеграции, в котором указаны тип интеграции, тип объекта, операция, интегрируемая система при явном выборе, идентификаторы и требуемая полнота данных.

Канонический запрос должен описывать, что нужно получить или изменить, но не должен раскрывать детали конкретной внешней системы. Например, вызывающий контур запрашивает задачу трекера и связанные цепочки обсуждения, а не конкретный набор полей GitHub или другого источника.

### Интеграционная операция

Интеграционная операция — нормализованное действие чтения или записи во внешнем источнике. Операция может получить объект, найти набор объектов, создать комментарий, открыть запрос на слияние, изменить признак задачи, связать объекты или выполнить другое внешнее изменение.

Операция является техническим элементом действия контура исполнения, если речь идёт о записи во внешний источник.

### Адаптер интеграции

Адаптер интеграции — модуль, который знает устройство конкретного внешнего источника. Он инкапсулирует авторизацию, формат вызовов, ограничения, преобразование ошибок и нормализацию результата.

Остальные контуры не должны зависеть от адаптера напрямую. Они обращаются к внутреннему интерфейсу контура интеграции.

### Настройки интеграции

Настройки интеграции описывают, как конкретная интегрируемая система подключается к комплексу.

В настройках указываются:

- тип интеграции;
- уникальное имя системы;
- признак системы по умолчанию для своего типа;
- ссылка на приватное значение для данных авторизации, если авторизация требуется;
- правила отображения внешних данных в канонические объекты;
- правила преобразования внешних полей задачи в признаки и атрибуты;
- сопоставление меток задачи, если внешние метки не должны передаваться один к одному;
- список поддерживаемых операций;
- ограничения источника, важные для повторного выполнения и диагностики.

## Внутреннее устройство

Целевой контур интеграции состоит из следующих частей.

Реестр контура интеграции принимает канонический запрос, определяет тип интеграции, выбирает интегрируемую систему, применяет правила доступа, вызывает встроенный адаптер или пользовательскую интеграцию и собирает итоговый интеграционный ответ. Наследуемая модель диспетчера не является частью публичного контракта.

Реестр типов интеграций описывает, какие типы интеграций доступны в комплексе, какие канонические объекты и операции относятся к каждому типу и какие пользовательские типы добавлены проектом.

Реестр интегрируемых систем хранит сведения о конкретных подключениях: тип интеграции, уникальное имя системы, признак системы по умолчанию, поддерживаемые операции и базовые ограничения. Значения авторизации и локальные параметры должны поступать из контура настроек и ресурсов.

Хранилище приватных значений предоставляет адаптерам интеграции токены, ключи и иные данные доступа по имени из настроек интегрируемой системы. Реализация хранилища выбирается отдельной настройкой. Для macOS вариантом по умолчанию является macOS Keychain. Контур интеграции получает значение в памяти процесса и не передаёт его через переменные окружения.

Встроенные адаптеры выполняют обращения к внешним системам, поддержанным в коде комплекса, и возвращают результат в промежуточной форме, пригодной для нормализации.

Исполнитель пользовательских интеграций запускает внешние `sh`-скрипты, передаёт им структурированный запрос и принимает структурированный результат. Для других контуров пользовательская интеграция должна выглядеть так же, как встроенная.

Нормализаторы приводят внешние данные к каноническим объектам выбранного типа интеграции. Для задач они отвечают за преобразование внешних статусов, меток, полей и связей в признаки и атрибуты.

Модуль операций изменения преобразует канонические операции записи в вызовы внешних систем и контролирует результат изменения.

Модуль отказов и частичных результатов приводит ошибки разных источников к единой диагностической модели: отказ авторизации, объект не найден, временная недоступность, превышение лимита, неподдерживаемая операция, неполный ответ, конфликт состояния.

Краткоживущий кэш удерживает данные только в пределах единичной обработки или явно заданного диагностического запуска. Он не является банком задач, контекстным архивом или источником текущего состояния.

## Обмен с другими контурами

### Контур реакции на внешние события

Контур реакции передаёт параметры, по которым нужно получить полный набор данных: тип интеграции, интегрируемую систему при явном выборе, тип объекта, внешний идентификатор, процесс реакции и требуемую глубину восстановления.

Контур интеграции возвращает каноническую задачу и связанные канонические объекты, достаточные для передачи в контур принятия решения.

### Контур принятия решения

Контур принятия решения получает от контура реакции уже восстановленные канонические данные. Для него контур интеграции задаёт форму объектов: признаки задачи, атрибуты, связи, комментарии, запросы на слияние, цепочки обсуждения и другие сведения, доступные маршруту обработки.

Контур принятия решения не должен работать с внешними форматами напрямую.

### Контур исполнения

Контур исполнения использует контур интеграции для операций чтения и записи, входящих в действие. Например, он может получить дополнительные сведения, оставить комментарий в трекере, открыть запрос на слияние в репозитории, изменить признак задачи или отправить сообщение в цепочку обсуждения.

Исполнение формирует операцию в канонической форме, а интеграционный контур отвечает за её применение к конкретной интегрируемой системе.

### Контур настроек и ресурсов

Контур настроек и ресурсов задаёт, какие типы интеграций и интегрируемые системы доступны, какие адаптеры включены, какие пользовательские `sh`-интеграции разрешены, какие параметры авторизации и ограничения применяются, какие локальные и проектные переопределения разрешены.

Контур интеграции использует эти сведения, но не должен сам становиться хранилищем проектных настроек.

### Контур журналирования и наблюдаемости

Контур интеграции передаёт диагностические сведения о каждом значимом вызове: тип интеграции, выбранная система, адаптер или пользовательская интеграция, операция, длительность, полнота результата, отказное состояние и внешний идентификатор результата.

Журналирование фиксирует сведения для диагностики и анализа, но не становится источником текущего состояния внешнего объекта.

## Каноническая задача и связанные объекты

Каноническая задача относится к типу интеграции «трекер» и является главным объектом обмена между интеграцией, реакцией и принятием решения. Она должна содержать описание ожидаемого результата, признаки, атрибуты, внешнюю ссылку, участников, состояние и связи с другими объектами.

Связанные объекты не являются внутренними частями задачи. Они остаются объектами своих типов интеграций и связываются с задачей через нормализованные связи. В зависимости от процесса реакции это могут быть:

- комментарии и обсуждения задачи;
- связанные запросы на слияние;
- замечания ревизии;
- сведения о репозиториях и ветках;
- цепочки обсуждения и сообщения мессенджера;
- документы и артефакты;
- дочерние и родительские задачи;
- ссылки на релизы, проверки и результаты внешних запусков.

Набор связанных объектов должен определяться процессом реакции, маршрутом обработки и требованиями действия. Контур интеграции должен поддерживать частичное восстановление данных, но обязан явно отмечать неполноту результата и тип интеграции, к которому относится каждый связанный объект.

## Признаки и атрибуты

Признаки задачи нужны как единый механизм коротких нормализованных состояний. Они могут быть получены из меток, статусов, пользовательских полей, связей, текста, правил адаптера или сочетания этих данных.

Преимущество признаков — простота маршрутизации и переносимость между источниками. Риск признаков — потеря структуры, если через них пытаться выразить сложные параметры.

Атрибуты задачи нужны для значений, у которых есть имя и содержательная величина: репозиторий, целевая ветка, приоритет, ссылка на среду, номер релиза, идентификатор внешней проверки. Атрибуты не должны заменять признаки там, где маршруту достаточно короткого нормализованного состояния.

Целевое правило: внешние метки, статусы и поля не передаются в другие контуры как есть. Адаптер должен преобразовать их в канонические признаки и атрибуты, сохранив при необходимости исходные значения в диагностических сведениях.

Сопоставление меток задачи задаётся на уровне интегрируемой системы. Если правило отсутствует, внешняя метка передаётся в каноническую задачу как признак с тем же названием. Если правило задано пустым значением, внешняя метка исключается из канонической задачи и не используется другими контурами.

## Операции изменения

Операция изменения должна быть описана так, чтобы контур исполнения задавал предметное намерение, а контур интеграции выбирал технический способ выполнения во внешнем источнике.

Примеры операций:

- создать комментарий к задаче;
- открыть запрос на слияние;
- добавить ссылку на артефакт;
- изменить признак задачи;
- связать дочернюю задачу с родительской;
- ответить на замечание ревизии;
- опубликовать сообщение в цепочке обсуждения;
- добавить реакцию к сообщению;
- добавить или снять метку задачи по каноническому названию.

Для операции изменения должны быть диагностируемы:

- целевой источник;
- тип интеграции;
- интегрируемая система;
- внешний объект;
- ожидаемое изменение;
- результат выполнения;
- внешний идентификатор созданного или изменённого объекта;
- признак повторяемости операции, если он доступен;
- отказное состояние при ошибке.

Идемпотентность не всегда может быть обеспечена самим контуром интеграции, потому что внешние системы различаются по поддерживаемым ключам повторного выполнения. Поэтому контур должен поддерживать ключ идемпотентности там, где это возможно, и явно сообщать вызывающему контуру, когда такая защита недоступна.

## Отказные состояния

Контур интеграции должен различать отказные состояния, которые требуют разных действий со стороны других контуров:

- не настроен внешний источник;
- отсутствует авторизация;
- недостаточно прав;
- объект не найден;
- внешний источник временно недоступен;
- превышен лимит обращений;
- операция не поддерживается адаптером;
- получен неполный ответ;
- обнаружен конфликт текущего состояния;
- внешняя система вернула неизвестную ошибку.

Отказное состояние должно содержать признак повторяемости. Это позволит контуру исполнения и очереди исполнения задач отличать временную ошибку от состояния, требующего ручного вмешательства.

## Расширяемость

Контур должен расширяться по следующим направлениям:

- новые типы интеграций;
- новые интегрируемые системы внутри существующих типов;
- новые классы канонических объектов;
- новые операции чтения и изменения.

Расширение не должно менять договорённости уже подключённых контуров. Новый адаптер или пользовательская интеграция подключаются через реестр интеграции, новые поля проходят через признаки и атрибуты либо через согласованное расширение канонической структуры, новые операции добавляются как отдельные интеграционные операции.

Практическое правило: если различие внешней системы важно только для получения или записи данных, оно остаётся внутри адаптера. Если различие важно для маршрута обработки или действия, оно должно быть выражено через канонический объект, признак, атрибут или отказное состояние.

## Вопросы для дальнейшей фиксации

Перед детальным проектированием контракта нужно отдельно зафиксировать:

- минимальный набор канонических объектов для трекера, репозитория и мессенджера;
- формат описания типа интеграции и интегрируемой системы;
- правила выбора системы по умолчанию и явного выбора системы в запросе;
- правила преобразования внешних меток, статусов и пользовательских полей в признаки и атрибуты;
- список операций чтения и изменения, обязательных для каждого базового типа интеграции;
- контракт пользовательской интеграции на основе `sh`-скрипта;
- модель цепочек обсуждения, сообщений и реакций сообщения для мессенджера;
- правила частичного восстановления связанных данных;
- формат ключа повторного выполнения для операций, где внешняя система позволяет избежать дублей;
- границу между краткоживущим кэшем интеграции и журналированием диагностических сведений.
