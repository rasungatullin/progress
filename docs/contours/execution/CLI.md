# CLI контура исполнения

## 1. Назначение документа

Настоящий документ фиксирует ручной интерфейс текущего среза контура исполнения.

Контур исполнения публикует только две операции:

- вызов действия через `progress execution action`;
- вызов операции через `progress execution operation <operation>`.

Остальные стадии остаются внутренними модулями контура. Они не являются отдельными публичными командами CLI и не принимают самостоятельный пользовательский вход.

## 2. Состав команд

В ветке `execution` доступны команды:

- `progress execution action`;
- `progress execution operation <operation>`.

Внешний вызов действия представлен моделью `ActionInvocation`. Внешний вызов операции представлен моделью `OperationInvocation`.

Команды `progress execution start`, `progress execution resume`, `progress execution dispatcher`, `progress execution profile`, `progress execution resources`, `progress execution workplace`, `progress execution launch` и `progress execution runs` не входят в текущий публичный контракт.

## 3. Входной контракт

### 3.1 Вызов действия

Вызов действия принимает только задание на выполнение `ExecutionAssignment`.

Через CLI задание собирается из:

- `--action` - имя действия;
- `--input-file` - путь к JSON-файлу структурированного ввода;
- `--task` - текстовая постановка структурированного ввода;
- `--constraint` - ограничение структурированного ввода, флаг можно повторять;
- `--project-context` - JSON-объект для `project_context`, флаг можно повторять;
- `--operational-context` - JSON-объект для `operational_context`, флаг можно повторять;
- `--previous-run-result` - JSON-объект для `previous_run_results`, флаг можно повторять;
- `--review-remark` - JSON-объект для `review_remarks`, флаг можно повторять; для замечаний ревизии допустимы поля `path`, `line` и `side`, где `line` относится к строке diff на выбранной стороне;
- `--review-response` - JSON-объект для `review_responses`, флаг можно повторять;
- `--integration-action` - JSON-объект для `integration_actions`, флаг можно повторять.
- `--repository` - репозиторий внешней системы в форме `owner/name`;
- `--task-number` - номер задачи для имени ветки и исполнительного рабочего места;
- `--pr-number` - номер запроса на слияние;
- `--base` - базовая ветка запроса на слияние;
- `--head` - ветка с изменениями для запроса на слияние;
- `--title` - заголовок задачи или запроса на слияние;
- `--body` - описание задачи или запроса на слияние;
- `--draft` - открыть запрос на слияние как черновик.

Если передан `--input-file`, файл загружается первым. Затем `--task` перезаписывает поле `task`, а повторяемые флаги добавляют элементы к соответствующим массивам. `extensions` на текущем этапе задаётся только через файл структурированного ввода.

Структурированный ввод опционален. Если structured-флаги и `--input-file` не переданы, вызов содержит только действие. Если структурированный ввод передан явно, он должен содержать хотя бы одно содержательное поле.

### 3.2 Вызов операции

Вызов операции принимает:

- имя операции в позиционном аргументе `<operation>`;
- то же задание на выполнение, что и вызов действия.

Операция выполняется только если она входит в разрешённое действие. Если операция отсутствует в составе действия, контур возвращает диагностируемый отказ `operation_not_in_action`.

## 4. Удалённые входные параметры

Внешний вызов действия и операции не принимает параметры внутренних стадий.

В публичном CLI отсутствуют:

- `--profile`;
- `--name`;
- `--dir`;
- `--repo`;
- `--runner`;
- `--model`;
- `--model-binding`;
- `--environment`;
- `--prompt`;
- `--structured-output`;
- `--structured-output-required`.

Профиль, рабочее место, исполнительный модуль, модель, окружение исполнения, директория запуска, требования к структурированному выводу и завершающие операции определяются внутри контура по разрешённому действию, заданию на выполнение, проектной конфигурации и доступным ресурсам.

Имя рабочего места не задаётся отдельным флагом. В текущей реализации оно выводится из номера канонической задачи в виде `<number>`, а при отсутствии номера из стабильного имени действия. Для действий инженерного цикла это же значение используется как имя ветки в отдельном `git worktree`.

Репозиторий можно передать флагом `--repository`; CLI помещает его в каноническую задачу и связанный запрос на слияние внутри `ExecutionAssignment`. Если репозиторий не передан явно, действие может получить его из структурированного задания или внутренней операции получения запроса на слияние.

## 5. Внутренний порядок исполнения

Вызов действия проходит по списку операций, закреплённому в разрешённом `Action.Operations`.

Контур исполнения получает от внешнего инициатора только имя действия в `ExecutionAssignment.Action`. Само разрешение имени выполняется через объединённый каталог методик из глобального и локального слоёв.

Для действия инженерного синтеза типовой порядок в поставляемом каталоге методик включает:

1. `resolve-action`;
2. `prepare-data`;
3. `resolve-profile`;
4. `allocate-resources`;
5. `prepare-workplace`;
6. `build-directive`;
7. `launch-synthesis`;
8. `parse-result`;
9. `finalize`.

Эти имена можно использовать для диагностического вызова `progress execution operation <operation>`, но сами стадии не становятся отдельными CLI-командами.

Поставляемый каталог методик содержит действия ручного инженерного цикла:

- `start-implementation-pr` - выполнить реализацию задачи, отправить ветку и открыть запрос на слияние;
- `review-pull-request` - проверить открытый запрос на слияние и записать замечания ревизии;
- `apply-review-comments` - получить замечания ревизии, исправить их, отправить ветку и записать ответы на замечания.

Состав этих действий также задан в каталоге методик. Действие `start-implementation-pr` включает операции `commit-push`, `publish-merge-request` и `publish-task-comment`, действие `review-pull-request` включает операции `load-pull-request`, `load-review-remarks` и `publish-review-remarks`, действие `apply-review-comments` включает операции `load-pull-request`, `load-review-remarks`, `commit-push` и `publish-review-responses`.

## 6. Выходной формат

Вызов действия печатает:

- `state=<status>` для итогового состояния;
- `summary<<PROGRESS_SUMMARY ... PROGRESS_SUMMARY` для текстового резюме;
- `raw-output-path=...`, если сохранён сырой вывод исполнительного модуля;
- `run-record-path=...`, если сохранена локальная запись запуска;
- секцию `structured-output:`, если получен структурированный вывод.

Для структурированного вывода печатаются:

- `summary-field=...`;
- `commit-message=...`;
- `remark=...`;
- `review-response=...`;
- `question=...`;
- `follow-up-action=...`;
- `change=...`;
- `command=...`;
- `conclusion=...`;
- `extension=...`.

JSON-строки структурированных секций выводятся без дополнительной нормализации пробелов, чтобы не терять исходный payload.

Вызов операции печатает:

- `operation=<name>`;
- `status=<status>`;
- `summary=<summary>`;
- сведения об отказе, если операция завершилась диагностируемой ошибкой.

## 7. Примеры

Вызов действия:

```bash
progress execution action \
  --action implement \
  --task "Подготовить изменение по задаче 123" \
  --constraint "Не менять публичный формат интеграционных ответов"
```

Вызов действия со структурированным вводом из файла:

```bash
progress execution action \
  --action review \
  --input-file .progress/execution/input.json
```

Начало реализации задачи с открытием запроса на слияние:

```bash
progress execution action \
  --action start-implementation-pr \
  --repository rasungatullin/progress \
  --task-number 112 \
  --title "Поддержать ручные действия инженерного цикла" \
  --task "Выполнить задачу по описанию и вернуть структурированный вывод"
```

Для `start-implementation-pr` рабочая ветка выводится из номера задачи. Если указан `--head`, он должен совпадать с этой веткой. Если указан `--base`, от этой же базовой ветки подготавливается новое рабочее место и к ней открывается запрос на слияние.

Ревизия открытого запроса на слияние:

```bash
progress execution action \
  --action review-pull-request \
  --repository rasungatullin/progress \
  --task-number 112 \
  --pr-number 17 \
  --task "Проверить запрос на слияние и вернуть замечания ревизии"
```

Для `review-pull-request` и `apply-review-comments` после загрузки запроса на слияние рабочее место открывается на его фактической ветке `head_ref`. Номер задачи сохраняет связь с постановкой, но не подменяет ветку проверяемого запроса. Если ветка `head_ref` недоступна локально и в `origin`, подготовка рабочего места завершается ошибкой.

Доработка по замечаниям ревизии:

```bash
progress execution action \
  --action apply-review-comments \
  --repository rasungatullin/progress \
  --task-number 112 \
  --pr-number 17 \
  --task "Исправить замечания ревизии и вернуть ответы на них"
```

Диагностический вызов операции разрешения действия:

```bash
progress execution operation resolve-action \
  --action review \
  --task "Проверить изменения по запросу на слияние"
```

## 8. Принцип проектирования

CLI контура исполнения должен оставаться тонким входом в две операции контура. Он передаёт действие или операцию и структурированный ввод, но не раскрывает наружу параметры внутренних стадий.

Если внешнему инициатору снова понадобится управлять профилем, рабочим местом, ресурсом или режимом запуска, это должно вводиться отдельным новым контрактом, а не восстановлением старых флагов.
