# Модель развития комплекса «Прогресс»

## 1. Назначение документа

Настоящий документ фиксирует направление развития комплекса после стабилизации базового маршрута задачи разработки. Документ описывает не календарный план, а целевую модель расширения возможностей.

Связанные документы:

- [docs/MOTIVATION.md](MOTIVATION.md) — основания и ключевые идеи;
- [docs/OPERATING_MODEL.md](OPERATING_MODEL.md) — модель работы комплекса;
- [docs/PLAN.md](PLAN.md) — поэтапный архитектурный план.

## 2. Базовый вектор развития

Развитие комплекса должно идти от минимального рабочего маршрута к конфигурируемой системе вложенных рабочих циклов.

Первый прикладной маршрут:

1. запуск по номеру задачи;
2. получение данных из внешнего трекера;
3. подготовка рабочего места;
4. кодирование;
5. создание запроса на слияние;
6. ревизия результата;
7. доработка замечаний;
8. повторная ревизия;
9. слияние при положительном заключении.

После стабилизации этого маршрута должны добавляться не отдельные разрозненные функции, а новые управляемые каскады и профили.

## 3. Вложенные рабочие циклы

Рабочие циклы должны допускать вложенность. Внешний процесс может соответствовать процессу команды: постановка, работа, тестирование, ревизия, готовность. Внутри отдельной стадии может действовать собственный вычислительный каскад.

Пример:

1. задача находится на стадии исполнения;
2. контур принятия решения выбирает каскад кодирования;
3. контур исполнения запускает изменение;
4. затем запускается ревизионный каскад другой моделью;
5. при наличии замечаний формируется повторное задание на доработку;
6. после положительного заключения управляющий контур переводит задачу к следующей стадии.

Такая модель позволяет развивать автоматизацию по частям и сохранять управляемость внешнего процесса.

## 4. Сосуществование с инженерами

Комплекс должен быть рассчитан на длительный переходный период, в котором автоматические и ручные действия сосуществуют.

Инженер может участвовать в следующих точках:

- уточнение постановки задачи;
- подтверждение запуска;
- согласование перехода между стадиями;
- разбор спорного заключения ревизии;
- принятие решения о слиянии;
- изменение правил маршрутизации или профиля.

При этом комплекс должен продолжать автоматизировать все стадии, которые уже могут быть выражены правилами и проверяемыми каскадами. Наличие ручной точки согласования не должно отменять автоматизацию остальной части маршрута.

## 5. Исполнительные модули

Комплекс должен поддерживать несколько исполнительных модулей. На начальном этапе это могут быть внешние CLI-инструменты и существующие среды запуска. В дальнейшем возможна собственная реализация исполнительной подсистемы.

Целевые требования:

- единый контракт запуска;
- единый структурированный ввод;
- единый структурированный вывод;
- фиксация выбранного модуля и модели;
- возможность резервного выбора;
- сравнение результатов и стоимости;
- изоляция прикладного маршрута от особенностей конкретного модуля.

Имена конкретных внешних средств, например `codex`, `opencode` или `pi`, должны оставаться деталями конфигурации и ресурсной привязки.

## 6. Модели и исполнительные профили

Выбор модели должен быть частью инженерной конфигурации. Для каждой категории задач могут отличаться:

- требуемый уровень качества;
- допустимая стоимость;
- объём контекста;
- форма исполнительной директивы;
- требования к структурированному выводу;
- необходимость ревизии;
- допустимость повторного запуска.

Один и тот же рабочий сценарий может иметь несколько профилей: экономичный, основной, усиленный или ревизионный. Профиль должен описывать не только имя модели, но и способ подготовки контекста, форму директивы и проверочные ограничения.

## 7. Навыки исполнения

Комплекс должен накапливать повторяемые инженерные знания в навыках и профилях исполнения.

Пример: добавление нового API-обработчика может иметь общую структуру:

1. найти существующие обработчики;
2. определить соглашение маршрутизации;
3. добавить тип запроса и ответа;
4. подключить обработчик;
5. добавить проверку;
6. вернуть структурированный результат.

Но фактическая исполнительная директива может отличаться для разных моделей. Модели с высоким качеством синтеза можно передать более компактную директиву, а экономичной модели требуется более явная последовательность действий, ограничения и формат ожидаемого вывода.

## 8. Настраиваемая системная директива

Комплекс должен предусматривать возможность переопределения системной исполнительной директивы для конкретной команды, репозитория, профиля или модели.

Это нужно для случаев, когда:

- команда использует особые правила кодирования;
- репозиторий требует специфичного порядка проверки;
- модель нуждается в иной форме ограничений;
- внешний исполнительный модуль имеет собственные требования к запуску.

Переопределение не должно разрушать общий контракт комплекса. Оно должно быть частью конфигурации, фиксироваться в записи запуска и быть доступным для диагностики.

## 9. Сравнительные прогоны

Для развития качества требуется механизм сравнительных прогонов. Комплекс должен позволять сопоставлять разные модели, профили и маршруты на похожих задачах.

Сравниваемые параметры:

- успешность выполнения;
- количество замечаний ревизии;
- стоимость запуска;
- длительность обработки;
- объём потреблённого контекста;
- количество повторных запусков;
- пригодность результата к слиянию.

Итогом таких сравнений должны быть изменения профилей, правил выбора модели и состава контекста.

## 10. Развитие через оптимизацию задач

Ключевой прикладной подход состоит в том, чтобы брать задачу как базовый сигнал, дополучать по ней данные, определять следующий шаг, выбирать контекст, модель, профиль и окружение, затем запускать исполнительный каскад и фиксировать результат.

Дальнейшее развитие должно улучшать каждый элемент этой цепочки:

- точность восстановления стадии задачи;
- качество отбора контекста;
- устойчивость исполнительных директив;
- экономичность выбора модели;
- качество ревизионных каскадов;
- надёжность внешних действий;
- полноту записи запуска.

Такой путь позволяет развивать комплекс не через разовые демонстрации, а через повторяемое улучшение производственного цикла разработки.
