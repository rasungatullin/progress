# План архитектурного развития

## 1. Назначение документа

Настоящий документ фиксирует поэтапный план формирования архитектуры комплекса «Прогресс». План ориентирован на начальную реализацию и предназначен для согласования состава работ до появления развёрнутой кодовой базы.

## 2. Основной принцип планирования

Развитие комплекса целесообразно вести от минимального рабочего контура к расширяемой вычислительной системе. На каждом этапе должен появляться законченный фрагмент архитектуры, пригодный для локальной проверки.

## 3. Этап 1. Каркас комплекса

Цель этапа — зафиксировать минимальную исполняемую структуру проекта.

Результат этапа:

- базовый Go-каркас;
- CLI-точка входа;
- загрузка конфигурации;
- базовое журналирование;
- пустые интерфейсы основных контуров.

Минимальные работы:

- определить структуру каталогов;
- ввести тип конфигурации комплекса;
- ввести общий тип сигнала;
- ввести общий тип задания на исполнение;
- определить интерфейсы координатора.

## 4. Этап 2. Контур реакции на внешние события

Цель этапа — обеспечить приём внешних сигналов в минимальной конфигурации.

Результат этапа:

- механизм периодического опроса;
- базовый обработчик webhook-вызова;
- нормализация сигналов к внутреннему формату;
- очередь или буфер внутренней передачи.

Минимальные работы:

- определить адаптеры источников событий;
- описать дедупликацию сигналов;
- определить признаки повторной обработки;
- ввести журнал регистрации событий.

## 5. Этап 3. Контур интеграции

Цель этапа — сформировать общий механизм получения данных из внешних систем.

Результат этапа:

- единый интерфейс интеграционного модуля;
- начальный набор адаптеров;
- механизм запроса данных по объекту задачи;
- унификация ответов во внутренние структуры.

Минимальные работы:

- определить контракт адаптера;
- ввести модель внешнего ресурса и артефакта;
- определить обработку ошибок недоступности;
- ввести кэширование повторных запросов при необходимости.

## 6. Этап 4. Контур принятия решения

Цель этапа — ввести управляемую схему выбора дальнейших действий по сигналу.

Результат этапа:

- классификация сигналов;
- атрибуция задачи и её инженерного типа;
- базовый анализ ограничений;
- запрос недостающих сведений через интеграционный контур;
- решение о выполнении, отложении или отклонении;
- формирование задания на исполнение.

Минимальные работы:

- определить тип решения;
- описать правила маршрутизации;
- ввести приоритет задачи;
- определить правила отложенного сигнала и повторного рассмотрения;
- определить требования к оперативному контексту.

## 7. Этап 5. Контур исполнения

Цель этапа — обеспечить выполнение задач в соответствии с решением управляющего контура.

Результат этапа:

- диспетчеризация исполнительных профилей;
- подготовка исполнительного рабочего места;
- подключение подсистемы ресурсного снабжения;
- запуск локальных вычислительных каскадов;
- фиксация промежуточных результатов;
- передача результата в верификацию.

Минимальные работы:

- определить интерфейс диспетчера исполнения;
- определить структуру исполнительного профиля;
- определить модель исполнительного рабочего места;
- определить модель ресурса, бюджета и резерва;
- описать модель шага исполнения;
- ввести статус выполнения;
- определить правила остановки и повторного запуска.

## 8. Этап 6. Проектное состояние и контекстный архив

Цель этапа — сделать обработку воспроизводимой и прослеживаемой.

Результат этапа:

- хранилище проектного состояния;
- журнал прохождения задачи;
- выделение оперативного контекста;
- архивирование завершённых каскадов и артефактов.

Минимальные работы:

- определить модель состояния;
- определить жизненный цикл задачи;
- определить формат архива;
- задать правила очистки и повторного включения контекста.

## 9. Этап 7. Контур верификации

Цель этапа — сделать проверку результата обязательной стадией обработки.

Результат этапа:

- базовые правила верификации;
- сопоставление результата с ограничениями;
- признаки успешного, частичного и неуспешного завершения;
- возврат задачи на повторное согласование при необходимости.

Минимальные работы:

- определить интерфейс верификатора;
- ввести тип результата верификации;
- описать переходы между стадиями после проверки;
- определить минимальный журнал проверок.

## 10. Этап 8. Координатор комплекса

Цель этапа — связать контуры в единый управляемый цикл.

Результат этапа:

- координатор прохождения сигнала по контурам;
- контроль последовательности стадий;
- обработка отказов и таймаутов;
- поддержка реконфигурации режима работы.

Минимальные работы:

- определить общий контракт контуров;
- зафиксировать порядок обмена данными;
- определить точки журналирования;
- определить правила аварийного завершения.

## 11. Ближайший практический приоритет

Для начала кодовой реализации рекомендуется ограничить первый рабочий срез следующей схемой:

1. CLI и конфигурация;
2. один источник внешнего сигнала по расписанию;
3. один интеграционный модуль-заглушка;
4. минимальный контур принятия решения по правилам;
5. один исполнительный профиль;
6. одно исполнительное рабочее место по пресету;
7. минимальная подсистема ресурсного снабжения;
8. журналирование и простая верификация результата.

Такая схема позволит получить минимальный замкнутый вычислительный контур без преждевременного усложнения архитектуры.
