## Базовый словарь

Базовый словарь содержит термины, уже используемые в существующих документах и кодовой модели. Часть этих терминов может быть перенесена или уточнена после согласования целевой архитектуры.

| Термин | Значение |
| --- | --- |
| комплекс | Проект «Прогресс» как единая инженерно-вычислительная система. |
| контур | Автономная часть комплекса с собственной ответственностью и формализованным внешним интерфейсом. |
| контур реакции на внешние события | Контур регистрации внешних событий, нормализации сигналов и запуска последующего цикла обработки. |
| контур интеграции | Контур получения, изменения и нормализации данных внешних систем через внутренний контракт. |
| контур принятия решения | Управляющий контур, который по сигналу, контексту и ограничениям выбирает следующий режим обработки. |
| контур исполнения | Контур выполнения формализованной задачи в изолированной вычислительной среде. |
| вычислительный каскад | Последовательность действий, модулей и инструментальных вызовов, выполняемых для достижения результата. |
| исполнительный каскад кодирования | Прикладной вычислительный каскад, выполняющий изменения в кодовой базе. |
| ревизионный каскад | Прикладной вычислительный каскад проверки результата и формирования замечаний ревизии. |
| сигнал | Нормализованное сообщение о внешнем событии или внутреннем повторном запуске обработки. |
| задача | Рабочий объект трекера или внутренний объект обработки, который проходит через контуры комплекса. |
| задание на исполнение | Практическая модель первого среза `ExecutionPlan`, которая содержит целевое задание на выполнение без параметров внутренних стадий контура исполнения. |
| решение | Результат работы управляющего контура: выбранный тип обработки, причины и возможное задание на выполнение. |
| маршрут обработки | Последовательность стадий обработки задачи. |
| оперативный контекст | Сведения, необходимые для текущего запуска и не являющиеся долговременной моделью состояния. |
| проектное состояние | Накопленное состояние проекта, используемое при принятии решения и верификации результата. |
| контекстный архив | Хранилище завершённых каскадов, состояний, артефактов и диагностических сведений. |
| структурированный ввод | Канонический входной JSON-контракт задачи для контура исполнения. |
| структурированный вывод | Канонический выходной JSON-контракт результата исполнения. |
| исполнительная директива | Итоговый текст запуска, собираемый контуром исполнения для исполнительного модуля. |
| исполнительный модуль | Внешний или внутренний механизм запуска вычислительного каскада. |
| исполнительный профиль | Преднастройка режима исполнения, требований к ресурсам, структурированному выводу и завершающим действиям. |
| привязка ресурсов | Правило выбора пары исполнительного модуля и модели. |
| исполнительное рабочее место | Подготовленная изолированная среда выполнения задачи. |
| запись запуска | Диагностический артефакт, фиксирующий вход, профиль, ресурсы, рабочее место и результат запуска. |
| запрос на слияние | Объект внешней системы для внесения изменений в основную ветку. |
| сообщение коммита | Краткое русское описание изменения, передаваемое в `git commit`. |
| замечание ревизии | Зафиксированное замечание по результату проверки. |
| ответ на замечание | Структурированный ответ на конкретное замечание ревизии. |
| заключение ревизии | Итоговая оценка готовности результата или необходимости доработки. |
| интеграционное действие | Операция чтения или записи во внешней системе через контур интеграции. |
| адаптер интеграции | Конкретный адаптер внешней системы, выбираемый диспетчером интеграции. |
| артефакт | Документ, файл, ссылка, результат запуска или иной объект, полученный либо созданный в процессе обработки. |

## Целевая терминология

Целевая терминология используется при описании новой архитектурной модели. После согласования контуров часть терминов из базового словаря должна быть перенесена или заменена этими определениями.

| Термин | Значение |
| --- | --- |
| внешний источник | Внешняя по отношению к основным контурам система, в которой хранится фактическое состояние рабочего объекта. |
| тип интеграции | Класс внешних источников с собственными каноническими объектами и типовыми операциями. |
| интегрируемая система | Конкретное подключение внешнего источника внутри типа интеграции с уникальным именем, настройками доступа и правилами отображения данных. |
| встроенная интеграция | Интеграция, поддержанная кодом комплекса через встроенный адаптер. |
| пользовательская интеграция | Интеграция, подключённая проектом через внешний `sh`-скрипт и соблюдающая канонический контракт контура интеграции. |
| настройки интеграции | Правила подключения интегрируемой системы: тип, уникальное имя, система по умолчанию, доступ, отображение данных, поддерживаемые операции и ограничения. |
| приватное значение | Именованное значение с ограниченным доступом, используемое для ключей, токенов авторизации и иных данных доступа без записи самого значения в проектную конфигурацию. |
| хранилище приватных значений | Реализация хранения приватных значений, выбираемая настройкой комплекса; например macOS Keychain или файловая реализация с ограниченными правами доступа. |
| канонический объект | Нормализованное внутреннее представление внешнего объекта, выражающее инженерный смысл объекта для маршрутов, проверок и действий комплекса. |
| каноническая задача | Нормализованное внутреннее представление внешнего рабочего объекта, с которым работает контур принятия решения. |
| канонический запрос | Обращение к контуру интеграции, описывающее тип интеграции, тип объекта, операцию, интегрируемую систему при явном выборе, идентификаторы и требуемую полноту данных без раскрытия деталей внешней системы. |
| цепочка обсуждения | Канонический объект мессенджера, объединяющий связанные сообщения и реакции. |
| реакция сообщения | Канонический объект мессенджера, фиксирующий короткую отметку пользователя на сообщении. |
| признак задачи | Нормализованный короткий признак канонической задачи, полученный из внешних меток, статусов, полей или правил адаптера. |
| метка задачи | Внешняя или каноническая метка трекера, которая в канонической задаче выражается через признак задачи. |
| сопоставление меток задачи | Настройка интегрируемой системы, переводящая внешние метки задачи в канонические названия или исключающая их из канонической задачи. |
| атрибут задачи | Нормализованное параметрическое поле канонической задачи для значений, которые не выражаются простым признаком. |
| страница документации | Канонический объект типа интеграции `wiki`, представляющий страницу внешнего хранилища документации. |
| интеграционная операция | Нормализованное действие чтения или записи во внешнем источнике через контур интеграции. |
| отказное состояние | Нормализованное описание ошибки, неполноты или недоступности внешнего источника с указанием возможности повторного выполнения. |
| задание на выполнение | Конкретное задание, сформированное контуром принятия решения для выполнения выбранного действия в контуре исполнения. |
| проверка | Чистое правило маршрута обработки, выбирающее задание на выполнение, переход к следующей проверке или завершение рассмотрения без побочных действий. |
| действие | Шаблон задания на выполнение, описывающий цель изменения и набор операций, которые должен выполнить контур исполнения. |
| операция | Технический элемент действия: интеграционный вызов, запуск исполнительного модуля, команда, скрипт, подготовка окружения или завершающий шаг. |
| нулевой этап исполнения | Начальная стадия контура исполнения, на которой входное указание сопоставляется с конкретным действием и фиксируется неизменный состав операций текущего запуска. |
| подмаршрут | Маршрут обработки, вызываемый из другого маршрута как отдельный участок процесса без внешних побочных действий. |
| контекст рассмотрения | Набор канонических данных, признаков, атрибутов, связанных объектов и параметров маршрута, используемых контуром принятия решения в одном цикле. |
| исход рассмотрения | Результат применения маршрута обработки: задание на выполнение, завершение, ожидание, ручное вмешательство или диагностируемый отказ. |
| основание решения | Структурированная причина выбора проверки, перехода, действия или иного исхода рассмотрения. |
| ручное вмешательство | Исход рассмотрения или выполнения, при котором дальнейшее автоматическое продолжение остановлено до изменения внешнего состояния человеком. |
| результат выполнения | Нормализованный итог работы действия: статус, резюме, структурированный вывод, артефакты, отказное состояние и диагностические ссылки. |
| инструкция для языковой модели | Подготовленное контуром исполнения указание, сформированное из действия, структурированного ввода, ограничений и требований к результату. |
| процесс | Описание реакции на внешние данные: источник наблюдения, частота, условия запуска и передаваемые параметры. |
| контур методик | Поддерживающий контур хранения переносимых маршрутов, действий, инструкций и рекомендаций по их применению. |
| контур настроек и ресурсов | Поддерживающий контур проектных, локальных и глобальных настроек, доступных ресурсов и разрешённых вариантов исполнения. |
| контур журналирования и наблюдаемости | Поддерживающий контур фиксации событий, решений, запусков, ошибок и диагностических сведений. |
| контур пользовательского интерфейса | Поддерживающий контур эксплуатационного доступа к настройкам, маршрутам, задачам, запускам и диагностике. |
| контур аналитики и статистики | Контур расчёта показателей работы комплекса по данным журналирования и дополнительным источникам. |
| банк задач | Набор задач и связанных данных для исследований, сравнительных прогонов и отладки методик. |
| контур исследований | Контур проверки гипотез об улучшении методик, маршрутов, профилей и настроек комплекса. |
| контур авторизации | Контур управления доступом к настройкам, данным запусков, просмотру сведений и внешним операциям. |
| очередь исполнения задач | Подсистема приоритизации и отложенного запуска задач, по которым уже принято решение о выполнении. |
| реестр контуров | Проверяемая кодовая карта контуров и межконтурных контрактов. |
| контракт межконтурного взаимодействия | Формализованный обмен между двумя контурами с объектом, описанием и инвариантами. |
| описание контура | Запись реестра с документационным именем, классом, пакетом реализации и документом. |
| внешнее событие | Сведения о внешнем изменении до нормализации в сигнал контура реакции. |
| каталог методик | Набор маршрутов обработки, действий и инструкций, доступных для выбора методики. |
| результат выбора методики | Выбранные маршрут, действие, инструкция и диагностические сведения выбора. |
| снимок настроек | Нормализованная сводка доступных настроек интеграции, исполнительных ресурсов и отказных состояний конфигурации. |
| диагностическое событие | Запись о значимом шаге работы контура, модуля или операции. |
| модель представления | Структура эксплуатационного раздела пользовательского интерфейса: раздел, панели и доступные действия. |
| субъект доступа | Пользователь, служба или иной источник операции, проверяемый контуром авторизации. |
| операция доступа | Запрашиваемое действие с указанием контура, вида действия и области применения. |
| политика доступа | Набор ролей и разрешений, по которому контур авторизации принимает решение о допуске. |
| решение авторизации | Результат проверки допуска к операции комплекса. |
| элемент очереди | Запись очереди исполнения задач с приоритетом, временем запуска, числом попыток и статусом. |
| отчёт показателей | Набор измерений, рассчитанных контуром аналитики и статистики по выборке запусков или событий. |
| измерение | Числовой показатель с именем, значением, единицей измерения и метками. |
| задача банка | Проверочная задача банка задач с входными данными, ожидаемым результатом и метками. |
| гипотеза исследования | Проверяемое предположение об улучшении методик, маршрутов, профилей или настроек комплекса. |
| эксперимент | Сравнительный прогон вариантов по гипотезе исследования на выбранном банке задач. |
| план эксперимента | Последовательность действий для воспроизводимой проверки гипотезы исследования. |
