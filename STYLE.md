# Стилистический регламент проекта «Прогресс»

## 1. Назначение документа

Настоящий регламент определяет требования к языку, тону и терминологии проекта «Прогресс». Документ предназначен для поддержания единого стиля описания комплекса в репозитории, архитектурных материалах, эксплуатационных пояснениях, CLI-справке и сопроводительной документации.

Цель регламента — обеспечить восприятие проекта как инженерно-вычислительного комплекса автономного синтеза и координации технических решений.

Документ является каноническим источником терминологии проекта. Если термин, сущность, модель или процесс закреплены в настоящем регламенте, дальнейшие тексты должны использовать это наименование без параллельных вариантов.

Для агентских контуров прикладные правила вынесены в `docs/AGENT_STYLE.md`, а обязательность соблюдения регламента зафиксирована в `AGENTS.md`.

## 2. Общий характер проекта

Проект должен восприниматься как:

- инженерно-вычислительный комплекс;
- инфраструктурная система;
- среда координации вычислительных контуров;
- система автономного инженерного синтеза;
- проектная и эксплуатационная основа для модульной вычислительной архитектуры.

Проект не должен восприниматься как:

- потребительское AI-приложение;
- диалоговый сервис;
- персонализированный цифровой помощник;
- демонстрационный AI-интерфейс;
- продукт с развлекательной или имиджевой подачей.

## 3. Стилистическая основа

В качестве смысловой и языковой опоры принимаются:

- советская и российская системная инженерия;
- кибернетика;
- автоматизированные системы управления;
- вычислительные комплексы;
- архитектурные материалы НИИ и КБ 1970–1980-х;
- инженерная и эксплуатационная документация;
- проектная инфраструктура технических систем.

Настоящая стилистика не является пародийной. Следует избегать карикатурности, ретрофутуристической стилизации и намеренного декоративного воспроизведения исторических форм.

## 4. Требуемые свойства изложения

Документация проекта должна быть:

- серьёзной;
- инженерной;
- функциональной;
- инфраструктурной;
- технологически строгой;
- концептуально цельной;
- сухой по тону, но читаемой.

Рекомендуемый характер изложения:

- технический;
- без маркетинговой экспрессии;
- без hype-лексики;
- без антропоморфных описаний системы;
- без разговорной интонации;
- без developer-meme культуры.

## 5. Образы, на которые должна быть похожа документация

Документация должна напоминать:

- описание вычислительного комплекса;
- материалы по архитектуре проектной инфраструктуры;
- системотехнические описания;
- эксплуатационную документацию;
- инженерные регламенты;
- документы по координации подсистем и контуров.

## 6. Формулировки, которых следует избегать

Не следует использовать терминологию и интонации, связанные с:

- chatbot-моделью;
- copilot-моделью;
- startup-лексикой;
- consumer AI-эстетикой;
- playful naming;
- cyberpunk-оформлением;
- personality-driven descriptions.

Недопустимые или нежелательные формулировки:

- «умный помощник»;
- «чат»;
- «бот»;
- `copilot`;
- `AI magic`;
- «делает всё за вас»;
- «революционный AI»;
- `next-generation assistant`;
- «интеллектуальный собеседник»;
- `thinking agent`.

Система не «думает», не «болтает», не «подсказывает как собеседник». Система принимает сигналы, выполняет анализ ограничений, координирует модули и проводит вычислительные каскады.

## 8. Перевод современных AI-концепций в язык системной инженерии

При необходимости описания современных подходов следует использовать инженерные эквиваленты.

Предпочтительные замены:

- `agent` → автономный модуль;
- `workflow` → рабочий цикл;
- `orchestration` → координация подсистем;
- `memory` → контекстный архив;
- `planner` → контур планирования;
- `reflection loop` → контур верификации;
- `tool calling` → подключение инструментальных модулей.

Для описания исполнительного контура и смежной документации дополнительно принимаются следующие замены:

- `structured input` → структурированный ввод;
- `structured output` → структурированный вывод;
- `prompt` → исполнительная директива;
- `runner` → исполнительный модуль;
- `execution profile` → исполнительный профиль;
- `review` → ревизия;
- `review cycle envelope` → канонический конверт цикла ревизии;
- `reply to review` → ответ на замечание;
- `coder` → исполнительный каскад кодирования;
- `pull request` → запрос на слияние;
- `commit message` → сообщение коммита;
- `trailing block` → завершающий блок;
- `execution contour` → контур исполнения;
- `decision contour` → контур принятия решения;
- `integration contour` → контур интеграции;
- `reactivity contour` → контур реакции;
- `runtime` → среда исполнения;
- `run record` → запись запуска;
- `launch` → запуск;
- `profile` → исполнительный профиль;
- `binding` → привязка ресурсов;
- `fallback` → резервный выбор;
- `issue` → задача, если речь идёт о рабочем объекте трекера; `issue`, если речь идёт о literal-объекте GitHub;
- `comment` → комментарий;
- `artifact` → артефакт;
- `provider` → адаптер интеграции;
- `route` → маршрут обработки;
- `signal` → сигнал;
- `context` → контекст.

Если английская форма требуется как literal-имя ключа, CLI-флага, тега, команды или иного программного интерфейса, она сохраняется без перевода. В описательном тексте приоритет всегда отдаётся русскому инженерному термину.

Если точный перевод невозможен, следует выбирать формулировку, которая сохраняет инженерный смысл и не переводит проект в лексику потребительских AI-систем.

## 11. Правила описания публичных моделей

Публичные модели межконтурного взаимодействия должны описываться в следующем формате:

1. русское документационное имя;
2. точное имя Go-типа, JSON-поля или CLI-флага в обратных кавычках;
3. контур-владелец или контур-источник;
4. роль объекта в межконтурном обмене;
5. ограничения использования, если они влияют на другие контуры.

Например: `ExecutionPlan` — задание на исполнение, формируемое контуром принятия решения для передачи в контур исполнения. В тексте документации используется «задание на исполнение», а `ExecutionPlan` указывается только при прямой ссылке на Go-тип.

Описания таких моделей не должны ограничиваться перечислением полей. Для каждой публичной сущности требуется коротко указать, какой объект предметной области она представляет и как он называется в документации.
